# 선언형 UI란
먼저 용어부터.

### Declarative[디클래러티브] 선언적인, 서술적인
무엇이 되어야 하는지를 기술하는 방식.

### Imperative[임페러티브] 명령적인, 명령형의
어떻게 수행해야 하는지를 명령하는 방식.

### 그래서?
명령형 UI는 상태의 변경과 갱신을 각각 지시해야 한다. 예를 들어 count 값의 증가와 UI의 count 값의 갱신 둘 다 프로그래머가 직접 지시해야 함.
선언형 UI는 상태의 변경만 지시하면 된다. count를 보게 해놓고 count 값을 증가시키면 알아서 count의 변경을 감지하고 자신이 보여주는 내용을 갱신한다.
짧게 요약하면 데이터의 변경과 화면의 변경 간 동기화 책임을 누가 갖고 있냐임. 내가 가지면 명령형, 프레임워크가 가지면 선언형.

```Swift
import SwiftUI

struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack(spacing: 20) {
            Text("Count: \(count)")
                .foregroundStyle(
                    count > 0 ? .green :
                    count < 0 ? .red : .gray
                )

            if count >= 10 {
                Text("Maximum reached!")
            }

            Button("Increase") {
                count += 1
            }
            .disabled(count >= 10)
        }
        .padding(30)
    }
}
```

# View as Value
SwiftUI의 View는 화면에 존재하는 UI 객체 자체가 아니라 UI를 기술하는 값(Value)이다.
SwiftUI에서는 UI 요소를 객체에 대한 참조가 아니라 값 타입으로 표현한다.

C#을 쓰는 WinForms에서는 Label 클래스의 인스턴스를 참조하여, 해당 객체의 속성을 변경한다. 기존 객체의 Text 프로퍼티를 수정하는 것이고 객체 자체는 계속 유지된다.
Swift에서도 기존 AppKit의 경우, NSTextField는 클래스고 해당 인스턴스의 프로퍼티를 변경한다.
SwiftUI에서 Text는 구조체다. 따라서 값 타입의 인스턴스다. 다른 변수에 대입하면 값 의미론에 따라 복사된다.
값을 생성하는 행위와 화면에 표시하는 행위는 구분된다.

### View는 실제 화면에 존재하는 객체인가?
아니다. SwiftUI의 View 값과 실제 화면을 구현하는 객체는 구분된다.
프로그래머가 작성한 SwiftUI 코드 -> View 값 생성 -> SwiftUI 프레임워크 -> 실제 UI 구성 및 화면 표시
SwiftUI의 View 값은 UI를 기술하는 데이터고, 실제 UI의 구현과 렌더링은 프레임워크가 담당함.

### 왜 이렇게 했을까? 무슨 장점 때문에?
값 타입의 장점은 다음과 같다.
1. UI 구성을 값으로 표현할 수 있다.
2. 데이터 흐름이 명확해짐.
3. 새로운 값으로 변경된 UI 구성을 표현할 수 있다. 기존 인스턴스를 수정하는 대신, 다른 프로퍼티 값을 가진 새로운 View 값을 사용할 수 있다.
4. SwiftUI가 변경 사항을 분석하고 필요한 UI를 갱신하는데 활용할 수 있다.

### View의 값은 계속 유지되는가?
SwiftUI의 View 값은 일시적일 수 있지만, 화면상의 View 정체성과 상태는 그보다 오래 유지될 수 있다.
SwiftUI는 View 값과 별개로 UI 요소의 Identity(정체성)를 관리.
View의 값 -> 변경되거나 새로 생성될 수 있음
View의 정체성 -> 여러 갱신에 걸쳐 유지될 수 있음
View의 상태 -> 정체성이 유지되는 동안 보존될 수 있음

### struct인데 @State가 어떻게 유지되는가?
@State를 쓰면 SwiftUI가 관리하는 상태 저장소와 연결. View 값이 새로 생성되더라도 같은 View 정체성이 유지된다면 기존 상태 저장소를 계속 사용할 수 있다.

### View Identity가 유지되는 기준은?
 SwiftUI에서 View Identity가 유지되는 기준은 SwiftUI가 이전에 존재하던 View와 현재 View를 동일한 View로 식별할 수 있는지 여부.
 1. Structural Identity(구조적 정체성): View 계층에서의 구조적 위치와 타입을 기반으로 식별.
 2. Explicit Identity(명시적 정체성): 프로그래머가 지정한 식별자(id)를 기반으로 식별.
 
#### Structural Identity
View 타입, 부모 View 내부에서의 구조적 위치, 동일한 조건 분기 등이 유지되면 같은 정체성으로 취급할 수 있다.

```Swift
if isEnabled {            
    CounterView(value: 10)        
} else {            
    CounterView(value: 20)        
}
```
위와 같이 작성할 경우 서로 다른 조건 분기에 선언된 View가 된다. 즉, 조건이 바뀌면 한 분기의 View가 제거되고 다른 분기의 View가 나타난다. -> 기존 CounterView의 정체성이 유지되지 않으며, @State가 초기화된다.
```Swift
CounterView(value: isEnabled ? 10 : 20)
```
위와 같이 작성하면 정체성을 유지하며, @State도 유지된다.

#### Explicit Identity
.id(_:) Modifier를 사용하여 정체성을 설정할 수 있다.
구조적 위치와 타입이 그대로여도 명시적 ID가 변경되면 새로운 정체성으로 취급되며, @State가 초기화된다.

#### 그 외에
다음과 같은 경우에 변경된다고 본다.
- if/else의 서로 다른 View 분기 사이 이동
- .id()에 전달하는 값 변경
- View가 계층에서 제거된 후 다시 추가

ForEach에서 데이터 ID를 유지한 채 순서를 변경하는 것은 유지된다.
동적 목록에서는 항목의 화면상 순서가 바뀌어도 안정적인 식별자가 있으면 같은 항목으로 추적할 수 있다. 구조적 위치가 항상 동일해야 할 필요는 없다.

### 정리하면
SwiftUI는 View 구조체의 메모리 주소를 정체성으로 사용하지 않는다. 구조체 값은 갱신 과정에서 새로 만들어질 수 있기 때문. 대신 Structural Identity, Explicit Identity를 활용하여 View의 수명을 관리한다. @State의 수명도 해당 정체성과 연결된다.

# View Tree
View들이 부모와 자식 관계를 이루며 구성된 계층 구조를 의미.

```Swift
struct ContentView: View {
    var body: some View {
        VStack {
            Text("Title")

            HStack {
                Text("Left")
                Text("Right")
            }

            Button("Click") {
                print("Clicked")
            }
        }
    }
}
```
이건 아래와 같은 View 계층.
```
ContentView
└── VStack
    ├── Text("Title")
    ├── HStack
    │   ├── Text("Left")
    │   └── Text("Right")
    └── Button("Click")
```
## Container View
다른 View를 포함하고, 특정 방식으로 구성하거나 배치하는 View. 예를 들면 VStack, HStack, ZStack, Group.

## View Tree와 Modifier의 관계
```Swift
Text("Hello")
    .foregroundStyle(.red)
    .padding(20)
```
SwiftUI의 Modifier는 일반적으로 새로운 View 값을 반환하기 때문에 
```
padding
└── foregroundStyle
    └── Text("Hello")
```
개념적으로 위와 같은 관계가 된다.

따라서 Modifier의 순서는 어떤 View 구성에 어떤 Modifier를 적용할 지 결정한다.

## 조건문과 View Tree
```
VStack
└── if/else
    └── true 분기
        └── Text("Enabled")
        
VStack
└── if/else
    └── false 분기
        └── Text("Disabled")
```
두 Text는 서로 다른 구조적 정체성을 가지고 각각 다른 조건 분기에 속함.
참고로 분기 변경 후 다시 돌아간다고 해서 이전 분기의 상태가 복원되지 않는다. 분기를 떠날 때 기존 View의 수명이 종료되었기 때문에 다시 등장한 View는 초기 상태에서 시작함.

# View Identity 중에서 특히 Explicit Identity
View의 Value는 변경되더라도 View Identity는 유지될 수 있다.
View에 명시적인 정체성 정보를 부여하기 위해선 .id() Modifier를 사용한다.
.id()에는 인자로 Hashable protocol을 준수하는 값들을 넣을 수 있다. (Int, String, Bool, UUID, ...)
.id()는 기존 View 인스턴스의 속성을 직접 수정하는 메서드가 아니며, 지정한 식별자가 적용된 새로운 View 값을 반환한다. 따라서 Modifier 체인에 사용가능.

# View Update
Update, Evaluate(표현식이나 계산을 수행하여 결과를 냄)
SwiftUI에서는 body의 재평가와 실제 화면의 재렌더링이 동일한 작업이 아님.
상태가 변경되면 새로운 상태를 바탕으로 필요한 UI를 갱신함.
> 상태 변경 -> SwiftUI가 변경 사항을 추적 -> 필요한 View의 body 재평가 -> 변경된 View 구성 반영 -> 필요한 레이아웃 및 렌더링 수행 -> 화면에 결과 표시
SwiftUI가 상태, 환경, 관찰 가능한 모델 등의 의존성 변화를 이용해 필요한 View를 갱신함.

### 상태 변경
```Swift
@State private var count = 0
// do something...
count += 1
```
count가 증가 했을 때 @State는 SwiftUI가 관리하는 상태와 연결되어 있으므로 SwiftUI는 이 상태의 변경을 UI 갱신에 활용할 수 있음. (@State나 관찰 가능한 모델 같이 연결된 데이터만 대상)

### 의존성 추적
```Swift
Text("Count: \(count)") // count에 의존
Text("Hello World!")    // count에 의존하지 않음
```
단, 둘이 같은 부모의 body에 있고, 해당 body가 재평가되면 의존하지 않는 Text 생성 표현식도 다시 실행될 수 있다. 이게 다시 그린다는 뜻은 아님.

### 실제로는?
View 값 생성 != body 평가 != 실제 화면 렌더링

### 그래서?
상태를 소유하고 읽는 View에 따라 갱신이 필요한 범위가 달라짐.
상태를 무조건 가장 하위 View로 이동하라는 뜻은 아님. 공유 데이터라면 적절한 상위 수준에서 관리.

### body에 무거운 연산 두지 않기
- 대량 데이터 분석
- 복잡한 반복 연산
- 파일 읽고 쓰기
- 네트워크 요청
- 데이터베이스 작업
- 오래 걸리는 동기 처리
이런건 하지 말자. body의 계산이 오래 걸리거나 지나치게 자주 발생하면 안됨. 현재 상태를 기반으로 UI를 빠르게 기술하는 역할에 집중해야 함.

### Xcode에서 SwiftUI 갱신을 분석하는 방법
Instruments(CPU, 메모리, 렌더링 등 애플리케이션의 실행 성능을 측정하는 도구)를 사용.

## 정리하면
State Change, Body Evaluation, View Update, Rendering
1. 상태가 변경되면 필요한 View만 재평가된다.
2. body 재평가 != 재렌더링

# Result Builder
여러 표현식과 조건문 등을 사용해 하나의 결과를 구성할 수 있도록 Swift 컴파일러가 코드를 변환해주는 언어 기능
```Swift
VStack {
    Text("...")
    if isEnabled {
        Button("...") {
            print("...")
        }
    }
}
```
VStack의 {}는 클로저인가? 클로저라면 Text를 여러 개 나열했는데 무엇을 반환하는가? if에 따라 반환되는 View 타입이 달라져도 괜찮은가? return을 작성하지 않아도 되는가? -> 이것들을 Result Builder의 힘으로 없앱니다.
Swift에서 Result Builder는 특별한 문법을 허용하는 컴파일러 지원 기능.
좀 더 정확히는 코드 블록 내부의 표현식과 제어문을 정해진 빌더 메서드 호출로 변환하여 하나의 결과를 구성하는 Swift 언어 기능.
-> 이걸 통해서 SwiftUI가 여러 View를 자연스럽게 나열하는 선언형 문법을 제공. 선언적인 DSL을 구성하기 위한 언어 기능.
> Domain-Specific Language(특정 목적에 맞게 설계된 표현 방식)

일단 VStack {}은 클로저임. 근데 일반 클로저와 다른 이유는 VStack의 콘텐츠 클로저에 @ViewBuilder가 적용되어 있기 때문.
```Swift
init(
    alignment: HorizontalAlignment = .center,
    spacing: CGFloat? = nil,
    @ViewBuilder content: () -> Content // 이거 있어서 됨.
)
```
### @resultBuilder와 @ViewBuilder
@resultBuilder는 Swift 언어 자체에서 제공하는 어트리뷰트.
```Swift
@resultBuilder
struct MyBuilder {
    // 빌더 메서드 정의
}
```
@resultBuilder는 특정 타입에 Result Builder 기능을 부여하는 역할을 하며, SwiftUI 전용 아님. 일반 Swift에서도 사용가능.

@ViewBuilder는 위의 @resultBuilder를 이용하여 SwiftUI에서 구현한 구조체. 프로그래머는 @ViewBuilder를 사용하여 SwiftUI View를 구성하는 클로저나 프로퍼티에 Builder 기능을 적용.

### 어떻게 하나의 결과로 만드는가?
Result Builder는 여러 표현식의 결과를 결합하는 메서드를 정의 할 수 있다. buildBlock() 같은게 있음.
```Swift
@resultBuilder
struct NumberBuilder {  // Int...는 가변 인자.
    static func buildBlock(_ numbers: Int...) -> [Int] {
        numbers
    }
}

func makeNumbers(
    @NumberBuilder content: () -> [Int]
) -> [Int] {
    content()
}

let numbers = makeNumbers {
    10
    20
    30
}
// 아래와 비슷한 형태.
//let numbers = NumberBuilder.buildBlock(
//    10,
//    20,
//    30
//)
print(numbers)  // [10, 20, 30]
```
### 조건문은?
buildEither(조건에 따라 선택되는 결과를 구성하는 메서드)를 사용. 조건문에 따라 콘텐츠를 구성하는 메서드.
```Swift
if isEnabled {
    Text("Enabled")
} else {
    Button("Enable") {
        isEnabled = true
    }
}
```
```
조건: isEnabled
       │
       ▼
     if/else
       │
       ├── true
       │     │
       │     ▼
       │  buildEither(first:)
       │
       └── false
             │
             ▼
          buildEither(second:)
```
_ConditionalContent<TrueContent, FalseContent> 같은 타입이 사용됨.
SwiftUI는 이 구조를 정체성 관리에도 씀.

else 없으면 ViewBuilder.buildIf를 씀.

### 그래서?
내가 직접 compute property를 만들거나 할 때 쓸 수 있다.
```Swift
struct ExampleView: View {
//    var message: some View {    // 일반적으론 여기서 두 표현식을 쓸 수 없음.
//        Text("Hello")
//    }
    
    @ViewBuilder
    var message: some View {    
        Text("Hello")
        Text("World")
    }
    @ViewBuilder
    func makeMessage() -> some View {
        Text("...")
        Text("...")
    }
    // 근데 사실 그냥 VStack 같은걸 반환하게 되면 @ViewBuilder 안 써도 되긴 함.

    var body: some View {
        VStack {
            message
            makeMessage()
        }
    }
}
```

@ViewBuilder는 여러 View를 하나의 콘텐츠로 구성, 조건에 따라 서로 다른 View 생성, View를 반환하는 compute property 작성, View를 반환하는 함수 작성, 사용자 정의 Container 작성 등에 사용한다. 

### Xcode 27 이상에서는 ContentBuilder 타입 별칭도 생김
